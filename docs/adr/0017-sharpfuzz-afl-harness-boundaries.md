# ADR 0017: SharpFuzz instruments parser dependencies, not the AFL harness

## Status

Accepted.

## Context

The agent fuzzes the Auditd record parser and the DeltaZulu.Forward batch
decoder with AFL++ and SharpFuzz. Establishing a reliable managed fuzzing job
required several rounds of troubleshooting because failures at different
layers produced similar AFL++ fork-server errors.

The original workflow instrumented `DeltaZulu.Agent.FuzzHarness.dll`. SharpFuzz
injects trace callbacks into instrumented branches, but the harness selects its
target before it calls `Fuzzer.Run`. Those callbacks therefore ran before
SharpFuzz initialized its shared-memory trace map. The resulting managed
`AccessViolationException` became `SIGABRT` and AFL++ reported `Fork server
crashed with signal 6` before receiving any input. Switching repeatedly between
`Fuzzer.Run` and `Fuzzer.OutOfProcess.Run` could not solve a failure that occurred
before either runner had completed initialization.

The Forward corpus added two separate complications:

- A valid MessagePack seed is generated by a test. GitHub container jobs expose
  a host-valued `github.workspace` while commands run in the container-mounted
  workspace. Relative paths may also be resolved from the test host's working
  directory instead of the workflow shell's directory. Both cases allowed the
  generator test to pass while the following `test -s` failed silently under
  `sh -e`.
- The checked-in `malformed.bin` is intentionally not a MessagePack map.
  `ForwardLogBatchCodec.Decode` rejects it with
  `MessagePackSerializationException`. Treating that expected rejection as an
  unhandled exception created a false crash, while selecting the first corpus
  file for a startup check made that check nondeterministic.

## Decision

The fuzzing boundary and workflow are governed by these rules:

1. **Keep the harness uninstrumented.** Instrument the assemblies containing
   the code under test: `DeltaZulu.Pipeline.dll` for Auditd and
   `DeltaZulu.Pipeline.dll` plus `DeltaZulu.Forward.dll` for Forward. This follows
   SharpFuzz's runner model, which excludes the fuzzing project assembly and
   instruments its dependencies.
2. **Use `Fuzzer.Run` by default.** `Fuzzer.OutOfProcess.Run` is reserved for
   surviving timeouts or uncatchable failures after fuzzing has started. It is
   not a remedy for pre-initialization trace-map failures and imposes process
   startup and trace-stability costs.
3. **Anchor generated corpus paths to the container shell's `$PWD`.** Pass the
   resulting absolute path to the seed-generator process and use that identical
   path for the subsequent non-empty-file assertion. Do not construct this path
   from `github.workspace`, and do not rely on the test host's current directory.
4. **Use a known-valid seed for startup verification.** Forward verification
   uses the generated `valid-batch.bin`; it must not use filesystem enumeration
   to choose an arbitrary corpus entry. Malformed entries remain in the AFL++
   corpus and are exercised during fuzzing.
5. **Classify format rejection separately from a crash.** Auditd
   `FormatException`, and Forward `InvalidDataException`, `FormatException`, and
   `MessagePackSerializationException`, are expected outcomes for untrusted
   bytes. The harness logs their type/message to standard error and returns
   normally. All other exception types escape the filter and remain findings.
   Tests exercise both a valid Forward batch and the checked-in malformed
   payload semantics so this classification cannot silently regress.
6. **Preflight before AFL++.** After instrumentation, execute the published
   harness once with a non-empty known seed. This exposes managed startup and
   instrumentation errors directly, before AFL++ reduces them to a fork-server
   signal report.
7. **Run managed fuzzing without AFL's memory cap and with an explicit timeout.**
   The smoke job uses `-m none -t 10000`; the workflow's `-V 60` remains the
   overall smoke-test duration.

## Troubleshooting sequence

Future failures should be diagnosed in this order:

1. Identify the exact failing shell command. A passing `dotnet test` followed by
   exit code 1 with no test failure usually means the next `test` assertion
   failed under `sh -e`.
2. Run the published harness directly with the exact seed. A managed stack trace
   here is more actionable than an AFL++ fork-server error.
3. If AFL++ still fails before input, rerun with `AFL_DEBUG=1`. A pre-input
   `AccessViolationException` points first to instrumentation executing before
   `Fuzzer.Run`, especially accidental instrumentation of the harness.
4. Verify the harness assembly is uninstrumented and the actual parser
   dependency is instrumented. Do not change process mode until this boundary is
   correct.
5. For Forward failures, distinguish malformed MessagePack rejection from an
   unexpected decoder exception. The former is logged and ignored; the latter is
   a finding.
6. Confirm generated seeds with the exact absolute path passed to the generator,
   and print or inspect that path when diagnosing container-only failures.

## Consequences

Positive:

- Coverage represents parser and codec behavior rather than harness dispatch.
- The fork server initializes before any instrumented target branch executes.
- Startup regressions fail with a managed exception in a dedicated step.
- Corpus generation behaves consistently between GitHub's host and container
  path namespaces.
- Expected malformed-input diagnostics remain visible without converting them
  into false findings.

Negative and accepted:

- Exception classification is part of the fuzzing contract and must track codec
  dependencies. A newly introduced expected decoder exception initially appears
  as a finding and must be reviewed before being added to the allowlist.
- Logging every expected rejection can produce substantial stderr output during
  a fuzzing run. This is accepted for diagnostic visibility; revisit sampling or
  aggregation if it materially harms throughput or artifact size.
- Dependency instrumentation must be updated if parser ownership moves between
  assemblies.
- The preflight proves startup with one valid seed, not correctness across the
  corpus; AFL++ and regression tests remain necessary.

## Alternatives rejected

- **Instrument the harness:** rejected because target selection runs before the
  trace map is initialized and reproduces the pre-input `SIGABRT` failure.
- **Use out-of-process mode as the general fix:** rejected because it addresses
  child failures after runner initialization, not instrumentation callbacks that
  execute before initialization, and it costs throughput and trace stability.
- **Use `github.workspace` for the generated seed:** rejected because container
  jobs can interpolate the runner host path rather than the mounted container
  path.
- **Use a repository-relative generator path:** rejected because the test host
  and workflow shell need not share a current working directory.
- **Select the first Forward seed for preflight:** rejected because directory
  enumeration is nondeterministic and malformed seeds are valid corpus members
  but invalid startup-success fixtures.
- **Catch every exception:** rejected because it would hide real parser defects.
  Only reviewed format-rejection types are caught.

## Revisit triggers

Revisit this decision if SharpFuzz changes its trace initialization model, parser
code moves to different assemblies, expected-rejection logging measurably reduces
fuzzing throughput, or repeated uncatchable failures/timeouts justify accepting
the cost of `Fuzzer.OutOfProcess.Run`.
